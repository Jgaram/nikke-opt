# 실험 33 — 역할 지문과 역할 벡터: 스킬을 읽지 않고 시뮬로 잰 역할로 계정 탐색 줄이기 (계획 초안)

> 니케가 딜러인지 버퍼인지 그 중간인지를 스킬 효과로 나누지 않고 **시뮬 결과(니케별 딜)로 재면**,
> 처음 보는 짝 · 신캐까지 예측하는 모델을 만들 수 있는가? 그 모델이 계정 탐색을 같은 품질에서 더 적은 시뮬로 끝내는가?

**상태: 계획 초안(2026-11-02) — 사용자 확인 전.** 회차 구성 · 판단 기준 · 예산은 확인을 받은 뒤 회차마다 사전 등록한다.
진행 방식은 [연구 회차](../../docs/SEARCH.md#연구-회차-계획--실험--해석--다음-방향-결정)를 따른다.

## 출처 — 사용자 논의(2026-11-02)

1. 덱을 짤 때 버스트 단계 · 무기는 당연히 본다. 스킬 효과에 따라 딜러 · 버퍼 · 그 중간이 갈리는데,
   스킬 효과는 복잡하고 상황마다 많이 달라져 하드코딩으로 나누기 어렵다.
2. 판단 기준은 시뮬 횟수다. 실사용 참고치: **우리 계산기(nikke-sim)로 계정 탐색 1~2분이면 적당하다.**
   **신캐 갱신은 느려도 된다 — 수시간이어도 괜찮다.** 계정 탐색 쪽이 빠른 것이 중요하다.
3. 실전 감(정답지 — 아래 「사용자 예시」):
   - 아니스 : 스타 · 리틀 머메이드 · 나유타 — 버퍼지만 본인이 우월 코드(우코)일 때는 유의미한 딜러 역할도 한다.
   - 리틀 머메이드 — 조합에 따라 딜량이 많이 바뀐다.
   - 브리드 : 사일런트 트랙 — 버퍼지만 토브와 같이 든 조합에서는 버스트를 쓰든 안 쓰든 딜이 유의미해진다.

## 왜 이것인가

- **지금 모델은 니케 이름을 외운다.** 실험 3 이후의 대리 모델은 「니케 원-핫 + 같은 덱 짝 원-핫」 릿지다.
  처음 보는 짝 · 신캐는 예측값이 없다 — 실험 15에서 짝 의존 신캐의 이어 붙이기가 실패한 원인(짝 정보 0)과 같다.
  상위 10% 안 순위 상관이 0.6이라([실험 3](../02_score_distribution/README.md#결과--실험-3-학습-가능성)) 최종 순위는 시뮬에 많이 맡긴다.
- **총딜 하나만 배운다.** 평가 결과에는 니케별 딜(`members`)이 이미 나온다([실험 31](../31_recent_seasons/run31.py) `run_members`).
  니케별 딜을 배우면 시뮬 1회에서 라벨이 5개이고, 「누가 누구의 딜을 올리는가」(버퍼 → 딜러)를 직접 볼 수 있다.
  지금까지의 기록(`*.jsonl.gz`)에는 총딜만 남아 있다.
- **계정 탐색 현황(실험 21 기록):** 고정 절차 P의 평가 수 중앙 4,713(조합 탐색 2,713 + 후처리 2,000).
  조합 탐색 4,000 실행이 계정당 384~604초(평가 약 3,590) — 0.2초/시뮬 · 4코어 약 20시뮬/초로 셈한 순수 시뮬 시간(약 3분)보다 길다.
  시뮬 외 계산(대리 모델 맞추기 · 5덱 조립) 몫이 클 수 있다. 1~2분 참고치는 약 20시뮬/초에서 **시뮬 1,200~2,400회 이하**이고,
  시뮬 외 계산을 넣으면 그보다 적어야 한다.
- 옛 기록은 쓰지 않는다 — 계산기 버스트 규칙이 바뀌었다(원본 `37e0030`, [실험 32](../32_primitive_control/README.md#출처)). 자료는 새 평가기로 만든다.

## 원칙

1. **스킬 텍스트 · 효과를 사람이 분류하지 않는다.** 역할은 평가기 출력(니케별 딜 · 총딜)으로 잰다. 스킬 해석은 평가기의 몫이고,
   평가기 내부를 import하지 않는다([작업 규칙](../../rules/workflow.md#저장소-경계)). 니케 속성은 버스트 단계 · 무기 · 코드(속성)만 쓴다 —
   `roster_ssr.json`(실험 10)처럼 계산기 공개 자료 `parsed_nikke.json`에서 이름 · `weapon_type` · `element_code`만 뽑는다(스킬 효과는 뽑지 않는다).
2. **역할을 칸으로 자르지 않는다.** 딜러 성분 · 버퍼 성분 · 상황 의존 정도를 연속값으로 남긴다. 상황 = 보스 속성(우코 여부) · 동료 · 버스트 사용 여부.
3. **사용자 예시는 확인용 정답지다(관찰).** 문턱 · 모델 설정을 맞추는 데 쓰지 않는다. 지문이 예시와 다르면
   평가기와 실전의 차이인지 지문이 놓친 것인지를 직접 시뮬로 가린다(계산기 정확도는 평가기 책임 — [목표](../../docs/GOALS.md#시뮬레이션과-실전의-역할)).
4. **모델은 출발점 · 후보 제안용이다.** 최종 판정은 180초 시뮬이다([평가 규칙](../../rules/evaluation.md)).

## 표현

### A. 역할 지문 — 측정

- **기준 덱 K개:** 새 평가기로 다시 돈 공유 사전 계산(전원 보유 · 상) 기록의 상위 구성에서, 서로 니케를 적게 나누도록(쌍 자카드 작게)
  탐욕으로 고른다. 버스트 단계마다 그 단계 자리가 있는 덱이 K개가 되게 한다. 고르는 규칙은 결과 전에 고정한다. K = 20(안).
- **넣어 보기:** 기준 덱 · 자리마다 **그 단계의 모든 니케 X**를 넣어 평가한다(X가 이미 든 덱은 뺀다).
  원래 니케의 몫은 덱 · 자리마다 같은 상수라 니케끼리 비교하면 빠진다 — 「평범한 대체 니케」를 따로 정하지 않아도 된다.
- **조건:** (a) 기본 적(속성 없음), (b) 보스 속성 = X가 우코인 속성(`enemy.code`, 실험 31 `options`와 같은 칸),
  (c) 기본 적 + X 버스트 안 씀(`operation.no_burst` — 실험 32의 원시 입력 표현).
- **지문(니케마다):**

| 성분 | 계산 | 뜻 |
|---|---|---|
| 본인 딜 | (a)에서 X 딜의 덱 대비 비율, 기준 덱 중앙 | 딜러 성분 |
| 동료 딜 변화 | (a)에서 나머지 4명 딜 합, 같은 덱 · 자리의 다른 X 평균 대비 | 버퍼 성분 |
| 누구를 올리나 | 동료 딜 변화를 동료의 단계 · 무기 · 코드별로 나눈 값 | 상황 의존(어떤 딜러와 맞나) |
| 우코 배율 | (b) 본인 딜 / (a) 본인 딜 | 우코 때 딜러가 되는 정도 |
| 흩어짐 | 본인 딜 · 동료 딜 변화의 덱 사이 사분위 범위 / 중앙 | 조합을 타는 정도 |
| 버스트 몫 | (a) − (c)의 본인 딜 · 동료 딜 | 자기 버스트가 만드는 몫 |

- **비용:** 니케마다 K × 조건 3 = 약 60회 → 177명 약 1.1만(실제 횟수는 단계별 자리 수로 정한다). 신캐 1명은 약 60회.

### B. 역할 벡터 — 학습

니케별 딜을 예측하는 모델이다. 총딜은 그 합이다.

  d(X | 덱) = b_X(상황) + Σ_{Y ∈ 덱, Y ≠ X} ⟨u_X, v_Y⟩ + r_XY(관측된 짝 보정, 강하게 규제)

- u_X = 「받는 쪽」(딜러 성분), v_Y = 「주는 쪽」(버퍼 성분), 차원 4~16(내부 검증으로). 비대칭이라 「Y가 X를 올린다」를 표현한다.
  아니스 : 스타 같은 중간형은 u · v가 모두 크고, 브리드 + 토브 같은 특정 짝은 내적 또는 r_XY가 맡는다.
- b_X(상황)는 우코 여부를 받는다. 육성 차이는 계정 탐색 중 그 계정 시뮬로 다시 맞춰 보정한다(지금 릿지와 같다).
- **새 니케 시작값:** 기존 니케로 「지문 → (b, u, v)」 회귀를 배워, 신캐는 지문만으로 벡터를 얻는다. 그 뒤 시뮬이 쌓이면 다시 맞춘다.
- CPU numpy로 맞춘다. 학습 시간을 시뮬 횟수와 따로 기록한다([탐색 설계](../../docs/SEARCH.md#개발사전-준비새-문제-탐색의-비용)).

### 비교할 모델

| 기호 | 모델 | 정보 |
|---|---|---|
| **M0** | 지금 릿지(니케 + 짝 원-핫, 총딜) | 기준선 |
| M1 | M0 + 지문 특징(니케 성분의 합 · 짝 성분의 곱) | 지문만의 효과 |
| M2 | 역할 벡터(니케별 딜) | 니케별 딜 학습의 효과 |
| M3 | M2 + 지문 시작값 | 둘의 결합 |

## 순서와 실험 32

- Q1 · Q2는 실험 32의 컨트롤 회차(R1~R4)와 독립이다. 새 평가기의 자동 버스트(레이어 끔 · 켬 중 실험 32 R0 결과를 보고 정함)에서 잰다.
- Q3의 기준 절차 A와 후처리 구조는 실험 32 결과를 따른다 — 실험 32 R3 이후에 돌린다.
- 실험 32가 사전 계산을 다시 돌릴 때 기록에 니케별 딜을 남기도록 공용 기록 형식을 맞추는 것이 이 실험의 첫 작업이다.

## 사용자 확인이 필요한 것

1. 실험 32와의 순서 — Q1 · Q2를 지금(실험 32 R0 뒤) 병행할지, 실험 32가 끝난 뒤 할지.
2. Q4에 실제 신캐 3명을 쓸지(S43 갱신 준비와 겸한다).
3. 사용자 예시 표의 「잡았다고 볼 모양」이 실전 감과 맞는지, 더 넣을 예시가 있는지.

## 범위 밖

보스 시간 패턴(2차 목표), 큐브의 역할 벡터 편입(다음 회차 후보), 실전 정확도, 계산기 자체의 정확도.
옛 평가기 기록의 재사용은 하지 않는다(버스트 규칙 변경).
