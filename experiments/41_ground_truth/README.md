# 실험 41 — 답안지: 작은 풀 전수 계산으로 진짜 최적 5덱을 알고 탐색을 채점한다

> 시즌 풀을 랭커 덱이 들어가는 40명 안팎으로 줄여 구조 규칙을 통과하는 스쿼드 **전부**를 계산하면 그 공간의 최적 5덱을 확실히 안다.
> 그 답안지로 (1) 랭커 5덱이 시뮬 안에서 정말 최적에 가까운지와 우리 A는 최적의 몇 %인지, (2) 최적 5덱의 스쿼드들이 개별 값 순위로 어디에 있는지
> (지금의 「상위 K 확장」이 원리상 닿는가), (3) 실전 덱별 딜과 시뮬 값이 얼마나 맞는지(계산기 문제인가), (4) 지금 절차를 같은 풀에서 시뮬 0으로 재생하면
> 최적에 몇 번 만에 닿는지를 잰다. 새 탐색은 이 표를 본 뒤 짠다(실험 42).

**상태: 계획(2026-11-04, 사전 등록 초안 — 실행 전). 실행은 다른 세션이 맡는다.** 진행 방식은 [연구 회차](../../docs/SEARCH.md#연구-회차-계획--실험--해석--다음-방향-결정)를 따른다.
판단 기준의 수치는 임시이며 1단계 실행 전에 확정 커밋한다. [§결정 필요](#결정-필요-실행-전-사용자)를 먼저 본다.

## 출처 — 사용자 논의(2026-11-04)

- 실험 36 · 38 · 39 · 40의 결론: 같은 계산기 · 같은 후처리에서 랭커 스쿼드로 짠 5덱이 우리 A와 비기거나 높다(10시즌 중 6시즌). 놓친 랭커 덱은 우리가 계산한 덱에서
  같은 단계 한 명만 다른 이웃인데 그 부모가 값 순위 500등 근처라 확장 대상이 아니었다. 후보 생성을 넓혀도(39 a · b), 대리 모델을 바꿔도(40 d) 묶음 값은 늘지 않았다.
- 사용자: 「딜량은 낮은데도 실제 랭커 덱을 잘 못 잡아내는 상황이라 이 방법은 못 쓴다. 처음부터 다시 해도 좋으니 뭐부터?」
- 답: 새 탐색을 짜기 전에 **답안지**부터 만든다. 지금까지는 정답을 모르는 채로 20만 시뮬짜리 실험을 8~10개 표본으로 돌려 ±0.5%를 가르려 했다.
  [탐색 설계](../../docs/SEARCH.md#풀-수-있는-문제인가)는 처음부터 「전수 탐색이 가능한 작은 공간에서는 최적해를 구해 검증에 쓴다」고 적어 두었지만 한 번도 하지 않았다.
- 사용자 결정: **시즌 셋.** 풀은 니케 전체가 아니라 일부이되 기준은 코드로 적힌 기계적 규칙이고, 답안지는 채점에만 쓴다. 실제 작업은 다른 세션.

## 원칙

1. **답안지는 채점용이다.** 탐색의 입력 · 학습 · 문턱 조정에 쓰지 않는다. 실험 38이 10시즌 랭커 덱을 정답지로만 쓰고 검증은 다른 시즌으로 한 것과 같은 원칙이다.
2. **풀 규칙은 코드로 적고 결과 전에 `pool41.json`으로 커밋한다.** 사람이 니케 이름을 고르지 않는다. 랭커 자료가 풀에 들어가는 것은 의도다 —
   랭커 덱이 들어 있어야 「탐색이 찾을 수 있었는데 못 찾았는가」를 채점할 수 있다.
3. **제품 탐색은 바뀌지 않는다** — 전체 풀을 받고 랭커 정보 없이 돈다. 답안지가 바꾸는 것은 채점 방식이다.
   (가) 같은 40명을 주고 답안지의 최적에 몇 번 만에 닿는가, (나) 전체 풀을 주고 답안지 값 이상을 찾는가.
4. **값의 기준은 사전 값이다** — 기본 레이어 1시뮬 · 계산기 기본 스펙(장비 8줄 Lv10) · 렐릭 베어 큐브 · 코어 없음. 실험 36 기록(우리 A · 랭커 덱 값)과 바로 비교된다.
   후처리(컨트롤 · 큐브 · 장비 옵션)는 이 실험 밖이다 — 실험 35 · 36에서 후처리는 덱 순위를 거의 바꾸지 않았다(loss 0.09%).

## 절차

### 1단계 — 전수 표 (시뮬)

- 구성마다 **기본 배치 순서** 1시뮬: 단계 순 1 · 2 · A · 3(실험 10 `arrange`), 같은 단계 안은 무작위 대신 **이름 가나다순**(결정론). 결과는 총딜과 니케별 딜(`members`).
- 기록: `run_log/S??/table.jsonl.gz`(구성 · 순서 · 값 · members). 공용 평가 캐시를 쓰므로 끊기면 같은 명령으로 이어 받는다(실험 36과 같다).
- 랭커 덱의 **랭커 순서** 값은 실험 36 `rankers.json`에 이미 있다(같은 평가기 값).

### 2단계 — 배치 순서 다듬기 (시뮬, 작음)

- 배치 순서는 한 구성 안에서 값을 중앙 19% 바꾸지만 구성 순위는 거의 지킨다(실험 2, ρ 0.97). 표 전체를 모든 순서로 돌리지 않는다.
- 대상: (a) 기본 순서 값 상위 2,000 구성, (b) 3단계 묶기에서 OPT의 97% 이상인 5덱에 든 구성 전부, (c) 랭커 상위 40 스쿼드.
  실험 9 「딜이 달라질 수 있는 순서」 후보(`ORDER_TOP` 방식)를 모두 돌린다(구성당 약 10). 약 2~3만 시뮬.
- 구성 값 = 본 순서 중 최고. 다듬은 값으로 3단계를 다시 돌려 OPT를 확정한다. 다듬은 뒤 97% 안에 새로 든 구성이 있으면 (b)를 한 번 더(최대 2번).

### 3단계 — 답안지 묶기 · 채점 (시뮬 0)

- **OPT** = 표의 구성 값으로 겹치지 않는 5덱을 정확히 묶은 최고 합(실험 9 `pack_vals`). 27만 행을 그대로 넣기는 무겁다 →
  값 상위 5,000으로 먼저 묶어 하한 LB를 얻고, 구성 s의 상한 = v(s) + (s와 니케가 겹치지 않는 구성 중 값 상위 4의 합)이 LB 미만이면 s를 뺀다.
  남은 구성으로 정확히 묶어 최적을 증명한다(`exact` 기록). 증명하지 못하면 LB와 「미증명」으로 적는다(결과 전에 가지치기가 해를 바꾸지 않음을 작은 표본 테스트로 확인).
- **경치:** OPT의 99% · 97% 이상 5덱 수, 그것들을 서로 J ≤ 0.2 대표로 묶은 큰 분류 수(실험 30 `class_map`), 랭커 대표 5덱과의 J(`nikke_opt/similarity.py`).
- **개별 순위:** OPT 5덱 각 스쿼드의 전체 표 순위(기본 순서 값 기준 · 다듬은 값 기준 둘 다).
  **R_need(x)** = OPT의 x% 이상인 5덱들 중 「가장 낮은 구성 순위」가 가장 높은 5덱의 그 순위 — 값 상위 K개만 보고도 x%에 닿으려면 K가 얼마여야 하는가.
- **비교:** 우리 A(실험 36 사전 값, 161~174명 풀 · 2만 구성 탐색) · 랭커 대표 · 1위 · 랭커 스쿼드 최선(실험 36 `rankers.json`, 표 값 중 높은 쪽) ÷ OPT.
- **실전:** `real_vs_calc` 덱(랭커 10명 이상)의 실전 중앙 딜과 표 값(다듬은 값)의 시즌 안 스피어만 ρ, (실전 ÷ 계산) ÷ 시즌 중앙 ≥ 1.4인 덱 수(실험 32 R0 규칙).

### 4단계 — 지금 절차 재생 (시뮬 0)

- 실험 10 `run_method` G+E(실험 36 A 사전 계산 절차, 실험 39 `run39.py` base 판)를 **풀 = `pool41.json`, 평가기 = 표 조회**로 돌린다.
  표 밖 구성 요청은 오류로 둔다(풀을 줄였으니 생기지 않아야 한다). 표에 없는 배치 순서 요청은 기본 순서 값으로 답하고 횟수를 센다(순서 다듬기 몫은 표의 다듬은 값).
- 시드 4개 × 예산 12,500(지금과 같다). 500평가마다 그때까지 계산한 구성으로 정확히 묶은 5덱 합 ÷ OPT를 적는다.
  지표: 99% · 97% 첫 도달 평가 수(미도달은 그대로), 12,500에서의 비율, 시드 중앙 · 최소.
- 같은 틀에 실험 39 a · b, 40 d를 넣는 것은 선택이다(코드가 있어 싸다). 새 탐색 설계는 이 표를 본 뒤 실험 42에서 한다.

## 판단 기준 (사전 등록 초안 — 수치는 임시, 1단계 실행 전 확정)

시즌마다 따로 읽고, 셋이 엇갈리면 시즌별로 적는다.

| # | 질문 | 조건 | 읽기 |
|---|---|---|---|
| 1 | 탐색이 놓친 몫 | OPT ÷ 우리 A − 1 ≥ 1% | 풀 안에서도 탐색이 못 찾은 몫이 있다. 1% 미만이면 이 풀 안에서는 탐색 문제가 아니다(전체 풀로 넓힌 효과는 별도) |
| 2 | 랭커 덱은 최적에 가까운가 | 랭커 스쿼드 최선 ÷ OPT ≥ 99% | 랭커 묶음이 시뮬 안에서도 최적에 가깝다 → 「시뮬이 랭커를 낮게 본다」가 아니라 「탐색이 못 간다」 |
| 3 | 상위 K 확장이 닿는가 | R_need(99%) ≤ 40 | 닿는다 → 지금 이웃 구조로도 되고 문제는 대리 모델 · 예산. 40 < R_need ≤ 500 → 후보 폭 문제. **> 500 → 개별 값 순위로는 원리상 못 찾는다 → 묶음 단위 탐색(실험 42)** |
| 4 | 지금 절차는 작은 풀에서 닿나 | 재생 12,500에서 OPT의 99% 도달 시드 ≥ 3/4 | 닿는다 → 문제는 전체 풀로의 확장(후보 선별)이다. 못 닿는다 → 이웃 · 대리 모델 문제가 작은 공간에서도 확인된 것 |
| 5 | 계산기 의심 | 실전 ρ < 0.6 또는 1.4배 낮은 덱 ≥ 2 | 그 시즌은 계산기 진단을 탐색 수정보다 먼저 한다 |

- 1 · 3 · 4의 조합이 실험 42(탐색 다시 짜기)의 설계를 정한다. 설계 후보가 둘이면 42에서 같은 표 위에서 시뮬 0으로 재생해 가른다.
- **관찰(판단에 안 씀):** 99% 5덱 수 · 큰 분류 수 · 랭커 대표와의 J, OPT 스쿼드의 값 구조(강한 하나 + 넷인가, 고른 다섯인가 — 니케별 딜), 2단계 순서 다듬기 이득 분포,
  우리 A · 랭커 덱이 표 순위 어디에 있는가.

## 범위 밖

후처리(컨트롤 · 큐브 · 장비 옵션), 코어 30, 계정 결손 · 육성 차이, 보스 시간 패턴, 새 탐색 설계(실험 42), 전체 풀의 최적(알 수 없다 — 답안지는 풀 안의 최적이고 전체 풀 탐색은 이 값 이상을 찾아야 한다).

## 한계 (미리 적음)

- 답안지는 랭커 자료로 고른 풀 안의 최적이다. 전체 풀에는 더 좋은 묶음이 있을 수 있다.
- 기본 순서 1시뮬 값은 다듬은 값보다 낮다. 상위 2,000 밖 구성의 다듬은 값은 모른다 — 다듬으면 올라올 구성이 있을 수 있다(실험 2 ρ 0.97로 드물다고 본다). 순위는 두 기준으로 다 적는다.
- 실전 덱별 딜은 랭커 육성 · 컨트롤 · 보스 패턴이 섞인 값이라 시즌 안 순위 상관으로만 본다.
- 시즌 셋이라 시즌별 결론이다. 셋이 같은 방향이면 다른 시즌으로 답안지를 늘린다.

## 실행 (다른 세션)

순서: `pool41.json` 커밋 → 판단 기준 수치 확정 커밋 → 1단계(시즌마다, 끊기면 같은 명령) → 2 → 3 → 판단 → 4 → `analyze` · 로드맵.
세션이 쉬면 컨테이너가 회수되어 백그라운드 실행도 꺼진다(실험 39 SESSIONS) — 긴 실행은 하네스 백그라운드로 붙이고 끝날 때까지 기다린다.

```bash
bash tools/setup_evaluators.sh                                        # nikke-calc-rs 83a6d54
python -I experiments/41_ground_truth/pool41.py                       # → pool41.json (결과 전 커밋)
source .cache/evaluators.env && python -I experiments/41_ground_truth/run41.py table --season 36    # 시즌마다 · 끊기면 같은 명령
source .cache/evaluators.env && python -I experiments/41_ground_truth/run41.py refine --season 36
python -I experiments/41_ground_truth/run41.py pack --season 36
python -I experiments/41_ground_truth/run41.py replay --season 36 --seed 0
python -I experiments/41_ground_truth/run41.py analyze                # → analysis.json · results.md
```
