# nikke-opt

승리의 여신: 니케 **솔로 레이드의 유력 편성 군집 탐색기**.

> 임의의 계정 육성과 보스 패턴이 주어지면, 허용된 평가 횟수 안에서 **조합의 뼈대가 다른 유력 후보군**을 찾는다.
> 각 후보는 중복 없는 5덱(25명)과 배치·큐브·컨트롤을 갖추고, **180초 전체 시뮬레이션으로 검증한 조건과 결과**를
> 함께 제시한다. 사용자가 여러 후보를 실전에서 비교할 수 있게 하는 것이 최종 목표다.

계산기는 만들지 않는다. 외부 계산기를 평가기로 붙여 쓰고, 이 레포는 **무엇을 돌려 볼지 고르고
어떻게 묶어 어떤 대안들을 제시할지**를 맡는다. 아래는 목표 명세이며, 구현·검증 현황은 「로드맵」에서 구분한다.

---

## 배경

- 니케는 라이브 서비스 게임이다. 신규 니케가 계속 추가되고 시즌마다 보스가 바뀐다 → 매 시즌
  조합을 다시 고민해야 한다.
- 지난 시즌의 "정답"은 어느 정도 나와 있다. 많은 유저의 시행착오가 공유되며 덱이 수렴하고,
  특히 랭커 덱은 기록이 남는다(에닉 → [`nikke-analysis`](https://github.com/Jgaram/nikke-analysis)가
  시즌 1–41, 6개 서버, 서버별 상위 50명 × 5덱을 덱별 딜·전투력과 함께 수집).
- 하지만 **사람마다 육성이 다르고, 신캐가 나오면 조합이 바뀌고, 보스가 바뀌면 최적 덱이 바뀐다.**
  남의 덱을 그대로 따라가는 것만으로는 내 계정의 최적해가 되지 않는다.
- 단순 로직(탐욕적 선택 등)으로는 안 된다. 좋은 1·2덱은 누구나 비슷하게 짜지만, 승부는 대체
  자원(서브 딜러·버퍼)을 3~5덱에 어떻게 나눠 쓰느냐에서 갈린다.
- 실전 컨트롤과 계산기 정확도 때문에 시뮬 순위가 실전 순위와 같지는 않다. 그 차이는 조합의 뼈대에 따라
  달라질 수 있다. **실전 비교 가치가 있는 서로 다른 대안**을 남기는 것도 탐색의 목적이다.

## 문제 정의

| | |
|---|---|
| **입력** | 보유 니케·육성 상태 · 보유 큐브·레벨·장착 제약 · 실행 가능한 컨트롤 범위 · 보스 조건과 시간에 따른 패턴 · 현재 니케 풀(신캐 포함) · **평가 예산 N** |
| **출력** | 뼈대가 다른 유력 후보군과 군집별 대표 편성안. 각 안의 5개 스쿼드·배치 순서·큐브·컨트롤·시뮬 결과·성립 조건·선택 근거 |
| **목표** | 높은 5덱 시뮬딜과 구조적 다양성을 함께 확보해, 사용자가 실전에서 비교할 가치가 있는 대안을 제시 |
| **제약** | 각 편성안 안에서 한 니케는 25명 중 한 번만 사용. 대안 편성안끼리는 공유 가능. 계정 자원과 운용 제약 준수. 평가는 **항상 180초 전체 시뮬레이션** |
| **성질** | anytime — 중단 시점까지 검증한 최고 성능과 유력 대안을 반환. 예산이 늘면 성능 개선과 새 뼈대 발견을 함께 추구하되, 미발견 군집이나 전역 최적의 보장은 하지 않음 |

### 궁극적 목표에 이르는 네 단계

네 단계는 기능을 확장하는 순서다. 2·3단계에서 앞 단계의 최종 후보만 남긴 뒤 옵션을 붙이는 고정 파이프라인을 뜻하지 않는다.

| 단계 | 탐색 대상 | 필요한 결과 |
|---|---|---|
| **1. 계정별 조합 군집** | 임의의 보유·육성 상태에서 조합과 배치 순서. 보스·큐브·컨트롤 조건은 명시해 고정 | 한두 명 교체의 유사안에 몰리지 않는, 뼈대가 다른 유력 후보군 |
| **2. 조합 + 큐브** | 1단계에 계정이 쓸 수 있는 큐브 배정을 포함 | 큐브와 조합의 상호작용을 반영한 후보군과 각 안의 큐브 배정 |
| **3. 조합 + 큐브 + 컨트롤** | 2단계에 실행 가능한 컨트롤을 함께 탐색 | 기준 컨트롤에서는 약하지만 다른 운용에서 강해지는 조합까지 포함한 후보군 |
| **4. 임의의 보스 패턴에 대응** | 3단계를 새로 주어진 보스 조건·시간 패턴에 적용 | 해당 보스의 랭커 정답이 없어도 계정에 맞는 조합·큐브·컨트롤 후보군을 구성 |

1·2단계의 고정 컨트롤도 평가기 기본값·니케별 운용 설정을 포함한 **특정 조건**이다. 「컨트롤 없음」으로 부르지 않는다.
큐브의 소유·레벨은 계정 입력이고 배정은 탐색 변수다. 컨트롤은 조작 대상·타이밍·방식 등 평가기가 표현할 수 있는 범위에서
다루되, 동시에 수행할 수 없는 수동 조작이나 사용자가 실행할 수 없는 운용을 유효한 해로 취급하지 않는다.

### 조합의 뼈대와 군집

- 주력 딜러·필수 지원 조합, 주요 시너지, 버스트 운용, 5덱 간 핵심 자원 분배를 구조 차이의 후보 기준으로 본다.
  컨트롤을 탐색하는 단계에서는 운용 방식도 함께 본다. **캐릭터 교체 수만으로 다른 뼈대라고 판정하지 않는다.**
- 개별 스쿼드의 군집과 최종 5덱 편성안의 다양성을 구분한다. 25명이 같아도 덱을 나누는 방식이 다를 수 있고,
  덱의 표시 순서만 바뀐 것은 새 편성안이 아니다.
- 군집은 유력 조합을 정리하고 탐색 중 보존하기 위한 수단이다. 한 뼈대의 상위 후보만 모아 사후에 나누는 것으로
  다른 뼈대의 발견을 대신하지 않는다. 서로 다른 출발점·틀 재구성도 평가할 수 있어야 한다.
- 성능이 부족한 조합으로 군집 수를 채우지 않는다. 군집 기준·대표 선택법·성능 허용 범위는 벤치마크에서 검토하고
  근거를 남긴다. 군집 수나 특정 군집화 알고리즘을 미리 정답으로 고정하지 않는다.

### 시뮬레이션과 실전의 역할

계산기 정확도와 게임 메커니즘 구현은 외부 평가기의 책임이다. 이 레포는 **실전과의 간극을 고려해 다양한 대안을 제공**하고,
각 대표안의 시뮬딜·기준안 대비 차이·배치·큐브·컨트롤·성립 조건과 미확인 사항을 설명한다.
대리 모델의 시뮬딜 예측 오차, 조작 조건 변화에 따른 성능 민감도, 계산기와 실전의 오차는 구분한다.
실전 자료가 없으면 어느 군집이 실제로 더 강한지나 계산이 더 정확한지는 미검증이다.

### 임의의 보스 패턴을 다루는 범위

4단계는 새로 주어진 패턴에서 편성을 찾는 목표다. 관측되지 않은 패턴 자체를 예언하는 기능은 아니다.
속성·방어력 같은 정적 값뿐 아니라 코어·파츠·공격 가능 구간·이동·페이즈 전환 등 시간에 따른 조건과
그에 맞춘 컨트롤을 입력·평가할 수 있어야 한다. 실제 지원 여부는 평가기 버전별로 확인한다.

패턴 자료를 평가기가 읽는 조건·스크립트로 연결하고, 출처·가정·버전을 기록한다. 새로운 기믹을 평가기가 표현하지 못하면
외부 평가기의 기능 확장이 선행되어야 한다. 미지원 기믹을 조용히 생략한 결과를 해당 보스의 검증된 편성으로 제시하지 않는다.
가상 보스의 방어력·속성만 바꿔 본 것으로 임의의 시간 패턴 대응이 검증됐다고 하지 않는다.

### 예산은 평가 횟수로 센다

예산의 단위는 **벽시계 시간이 아니라 180초 시뮬레이션 횟수**다. 평가기 속도는 엔진 교체·병렬화·
포팅으로 얼마든지 바뀌지만(참고: 딜도로 제작자는 Rust 포팅을 속도 개선 방법으로 꼽는다), "몇 번 돌려서
얼마나 좋은 답을 찾았나"는 엔진과 무관한 탐색 알고리즘의 성능이다. 시간 제한이 필요하면
`시간 ÷ 평가 1회 비용`으로 횟수로 바꿔 넘긴다. 계산 속도 최적화는 당분간 이 레포의 관심사가 아니다.

| 예산 N (감각) | 의미 |
|---|---|
| ~10회 | 5덱 한 벌 검증이 5회. 사실상 **사전 지식이 답을 내는** 구간 |
| ~수백 회 | 사전 지식 + 국소 개선 |
| ~수천 회 이상 | **탐색이 주도하는** 구간 |

큐브·컨트롤·보스 조건을 바꿔 실제 시뮬을 추가하면 각각 예산을 쓴다. 작은 예산에서는 충분한 군집을 찾지 못할 수 있으므로
발견·검증한 범위를 보고한다. 벤치마크는 기준선 준비와 탐색에 든 비용, 사전 계산·캐시로 제공한 지식을 따로 기록하고
비교 방법에 같은 출발 정보와 예산을 준다.

### 풀 수 있는 문제인가

- **전역 최적의 증명은 불가능하다.** 평가기는 블랙박스이고, 보유 100명이면 5인 조합만 약 7,500만
  개에 배치 순서가 곱해진다.
- **예산 안에서 유력한 대안을 발견하는 능력을 잰다.** 아래 [벤치마크](#성능-측정)에서 최고 성능과
  유력 뼈대의 발견 범위를 함께 평가한다. 한 군집의 국소 최적에 도달한 것으로 다른 군집까지 탐색했다고 보지 않는다.
- **게임 규칙을 하드코딩하지 않는다.** 버스트 순서·버충량·쿨감·시너지는 이미 평가기 안에 있다.
  이 레포가 푸는 것은 "비싼 블랙박스를 무엇으로 몇 번 돌려 볼까"(블랙박스 최적화)다. 구조 특징은 후보 생성·군집화에도
  쓸 수 있지만, 좋은 조합을 하드코딩하거나 과거 빈도가 낮다는 이유로 가능성을 제거하지 않는다.
- **학습용 딜 라벨은 계정·보스·운용 조건별 시뮬 결과다.** 실전의 정답을 뜻하지 않는다. 랭커 데이터는 딜 수치로 쓸 수 없으므로
  (아래 「지식의 세 출처」) 라벨이 아니라 "무엇부터 돌려 볼지"의 사전 지식이다.

## 핵심 구조: 스쿼드 탐색과 5덱 조립을 연결한다

덱끼리는 서로 영향을 주지 않는다(같은 보스를 각자 따로 친다). 따라서
**총점 = 스쿼드 점수의 합**이다. 다만 캐릭터 중복과 계정 자원 제약 때문에 독립적으로 좋은 스쿼드 5개를
고르는 것만으로는 편성안이 되지 않는다. 큐브 재사용·장착 한도 등은 실제 게임 규칙을 확인해 적용한다.

1. **어떤 스쿼드가 좋은가 — 어려운 부분.** 평가가 비싸고 시너지가 합산되지 않는 블랙박스다.
   조합·배치·큐브·컨트롤을 해당 단계의 탐색 변수로 삼고, 유력한 여러 뼈대의 기록을 유지한다.
2. **자원 제약을 지켜 5덱으로 조립한다.** 기본 형태는 가중 집합 패킹이다. 기존 실험은 평가한 후보 풀에서
   딜 합이 가장 높은 한 벌을 분기 한정으로 정확히 고른다. 이는 전체 탐색 공간의 전역 최적을 뜻하지 않는다.
   목표는 성능과 구조가 다른 여러 편성안을 반환하도록 확장하는 것이다.
3. **조립 결과를 다음 탐색에 되먹인다.** 한 덱의 점수만 올리는 수뿐 아니라 핵심 자원 이동·여러 덱 재구성으로
   전체 편성안과 후보군을 개선할 수 있는 수를 고른다. 여러 뼈대를 유지하는 기능은 아직 미구현이다.

## 지식의 세 출처

| 출처 | 강점 | 약점 |
|---|---|---|
| **랭커 덱** (에닉 → `nikke-analysis`) | 수많은 시행착오가 걸러진 결과. 사용률(티어)·자주 붙는 짝·버스트 구성 틀이 드러나 있고, 보스가 바뀌어도 대략적 추세는 비슷하다 | **딜 수치는 쓰지 않는다** — 랭커의 육성 정보가 없고, 과거 보스는 시뮬레이터에 없어 시뮬딜과 맞춰 볼 수 없다. 신캐·새 보스에는 기록이 없다 |
| **시뮬레이터** (외부 계산기) | 명시한 육성·보스·운용에서의 시뮬딜 | 비싸고, 실전 정확도·미지원 기믹은 별도 확인이 필요 |
| **구조 특징·제약** (버스트 단계 B1/B2/B3, 역할, 자원 한도 등) | 불가능한 후보 제거와 후보 생성·군집 구분에 활용 | 특징만으로 실제 시너지나 좋은 조합을 확정할 수 없음 |

## 접근 (초안)

```text

     │
     ▼
```

- **다양성은 탐색 중에도 유지한다.** 다중 출발·큰 틀 재구성·군집별 유력안 보존을 기존 국소 탐색과 비교한다.
  방법은 [`AI_분석가이드.md`](AI_분석가이드.md)에 따라 기준선과 소수 후보부터 검증해 고른다.
  군집화만으로 좋은 조합이 생성되지는 않으며, 특정 모델이나 군집 수를 먼저 확정하지 않는다.
- **큐브·컨트롤은 조합과 함께 탐색한다.** 고정 운용에서 낮게 나온 조합을 영구 탈락시키고 상위만 운용 최적화하면
  놓치는 후보가 생길 수 있다. 모든 곱집합을 전수 평가할 필요는 없지만 다른 운용과 결합한 가능성을 평가할 기회를 둔다.
- **대리 모델은 다음 평가를 고르는 보조 수단이다.** 기존 「니케 + 짝」 회귀를 기준선으로 삼을 수 있다.
  계정을 넘는 모델은 육성, 운용을 넘는 모델은 큐브·컨트롤, 보스를 넘는 모델은 패턴 정보를 다뤄야 한다.
  모델의 예측 오차와 불확실성은 별도 검증하고, 최종 추천은 실제로 평가한 결과에 근거한다.
- **시즌 단위 사전 계산.** 보스가 공개되면 표준 육성으로 유력 스쿼드를 미리 돌려 캐시를 만들어 둔다.
  다른 계정·보스·운용에서는 후보 생성의 사전 지식으로 쓰되, 조건이 다른 결과를 캐시 적중으로 취급하지 않는다.
- **신캐 대응.** 랭커 데이터가 없으니 스킬 데이터에서 역할 태그를 뽑아 비슷한 기존 니케의 지식을
  빌리고, 부족한 만큼은 시뮬레이션으로 채운다.
- **새 보스 적응.** 과거 보스의 지식은 출발점으로 쓰고 새 패턴에서 다시 탐색·검증한다.
  여러 보스를 함께 학습하는 조건부 모델은 검토할 방법 중 하나다. 임의 패턴 대응을 특정 모델 도입과 동일시하지 않는다.
  정적 조건뿐 아니라 시간 패턴·컨트롤 상호작용을 분리해 시험한다.

## 성능 측정

다음은 새 목표를 위한 검증 계획이다. 시뮬 성능·구조적 다양성·실전 유효성을 구분하고, 실전 자료가 없는 항목은 미검증으로 남긴다.

| 관점 | 평가할 것 |
|---|---|
| 성능 | 같은 계정·보스·자원·평가 예산에서 랭커 이식, 기존 국소 탐색 등 기준선 대비 최고 5덱 합과 각 대표안의 성능 차이 |
| 유력 뼈대 발견 | 사전에 정한 성능 기준을 만족하는 서로 다른 뼈대의 발견 수·중복 정도. 작은 탐색 공간의 참조 후보군 대비 누락도 확인 |
| 군집의 의미·안정성 | 구조 차이를 설명할 수 있는지, 군집 기준이나 탐색 시드를 바꿔도 주요 대안이 유지되는지. 멤버 교체 수나 군집 수만으로 성공 판정하지 않음 |
| 공동 탐색의 효과 | 조합을 먼저 확정하고 운용을 붙이는 기준선과 조합·큐브·컨트롤 공동 탐색을 같은 총예산으로 비교. 컨트롤에 따라 순위가 역전되는 후보를 발견하는지 |
| 계정·보스 대응 | 개발에 쓰지 않은 보유·육성 조건과 보스 패턴에서의 성능·군집 발견. 정적 속성 변경과 시간 패턴 변경을 구분 |
| 실전 비교 가치 | 대표안의 운용을 재현할 수 있는지, 가능한 조작 변화에서 결과가 얼마나 변하는지. 실제 딜과의 차이·순위는 실전 자료로 별도 확인 |

- **참조값의 범위를 명시한다.** 작은 로스터·제한된 운용 공간에서 전수 탐색했다면 그 공간의 최적해·유력 군집과 비교한다.
  큰 예산 탐색으로 얻은 값은 알려진 최고값이며 전역 최적의 증명이 아니다.
- **예산별로 함께 보고한다.** N = 10 · 100 · 1,000 · 10,000 등의 시점에서 최고 성능, 대표안 성능, 발견한 유력 뼈대를 기록한다.
  초기 기준선 평가·운용 대안 평가도 비용에 포함하고, 사전 계산·캐시 사용량은 구분한다.
- **새 계정·보스 검증에서는 적용 상황에 맞게 자료를 나눈다.** 미관측 계정·패턴으로의 일반화와 새 타깃에서 시뮬을 추가한 후의 적응을
  구분한다. 적응용 시뮬은 허용된 예산으로 세고, 미래 랭커 결과나 평가용 참조해는 후보 생성·튜닝에 섞지 않는다.
  같은 뼈대의 유사 조합이 양쪽에 섞여 새 뼈대 예측력을 부풀리는지도 확인한다.
- **성공 기준은 실험 전에 정한다.** 허용 성능 차이·대표안 수의 상한·구조 구분법과 실용적 개선 기준을 기록한다.
  구체적 수치와 방법은 아직 미정이며, 분석 가이드에 따라 검증 결과와 미확인 사항을 구분한다.

### 기존 사전 실험의 조건과 적용 범위

- **육성**: 실험 2–4는 전원 기본 스펙, 실험 5는 가상의 결손·육성 등급 8개 시나리오다. 임의의 실제 계정 전반은 미검증이다.
- **보스·운용**: 실험 2–5는 S40와 정해진 큐브·컨트롤 조건이다. 당시 확인한 레이드 프리셋은 S40 하나였다.
  보스 파라미터 입력 기능이 있어도 미관측 시간 패턴에 대한 적응 성능이 검증된 것은 아니다.
- **검증한 목표**: 기존 결과는 단일 최고 편성의 시뮬 성능을 다룬다. 유력 군집 발견, 큐브·컨트롤 공동 탐색, 임의 패턴 대응은 미검증이다.

### 사전 실험 (본격 구현 전에 "풀 만한가"를 확인)

1. **경향 안정성** — 랭커 데이터만으로, 시즌(보스)이 바뀔 때 사용률 순위·자주 붙는 짝이 얼마나
   유지되는지 잰다. 사전 지식을 얼마나 믿을지 정한다.
   **→ 완료** ([결과](experiments/01_trend_stability/README.md)): 니케 단위는 잘 맞고(과거 기반 상위 50명이
   이번 주력 25명의 90%, 나머지는 주로 신캐), 과거 스쿼드 ±1명이 덱의 76%를 덮는다. 짝은 보스마다 크게 바뀐다.
2. **점수 분포** — 한 보스·한 로스터에서 구조 규칙을 통과한 무작위 스쿼드 1~2천 개를 180초로 돌려
   딜 분포를 본다. 상위권이 얼마나 뾰족한지, 유효 후보가 얼마나 되는지.
   **→ 완료** ([결과](experiments/02_score_distribution/README.md), S40·풀 60명·기본 스펙·시뮬 1,849회):
   유효 후보가 극히 드물다 — 무작위 1,500개의 최고가 랭커 구성 1위의 62%이고, 랭커 구성 중앙값이 무작위 99백분위다.
   이 조건에서는 균등 탐색보다 사전 지식이 유리했다. 배치 순서는 한 구성 안에서 중앙 19%(최대 2배)를 바꾸지만
   구성 순위는 거의 그대로였다(Spearman 0.97). 상위 구성만 순서를 다듬는 기준선의 근거이며, 큐브·컨트롤 후처리의 근거는 아니다.
3. **학습 가능성** — 2의 데이터로 "니케 단위 + 짝" 단순 모델이 처음 보는 조합의 순위를 맞히는지
   (순위 상관) 본다. 대리 모델이 필요한지, 가지치기 + 전수 탐색으로 충분한지 가른다.
   **→ 완료** ([결과](experiments/02_score_distribution/README.md#결과--실험-3-학습-가능성)): 「니케 + 짝」 릿지가
   교차검증 Spearman 0.86, 분포 밖(랭커 구성)에서도 0.79. 400개면 0.83. 상위 10% 안의 순위는 0.6이라 최종 판정은 시뮬로.
   짝을 타는 핵심 니케(솔린 : 프로스트 티켓·토브·프리카)는 단독 평균으로 보면 오히려 손해라 짝 항이 필요하다.
4. **개선 여지** — 큰 예산으로 찾은 최선 5덱 vs 랭커 구성 기준선. 시뮬 성능 개선을 재는 실험이다.
   랭커 빈출 스쿼드가 이번 보스 시뮬에서도 상위권인지도 함께 보아 사전 지식의 쓸모를 잰다.
   **→ 1차 완료** ([결과](experiments/04_improvement_margin/README.md), 평가 801회): 이 조건과 탐색에서는
   랭커 1위 5덱 309.3억 → 탐색 310.9억(+0.5%). 다른 뼈대의 최적성은 확인하지 않았다. 상위 스쿼드 근처만 파면 1덱만 강해지고 다른 덱과
   겹쳐 합이 그대로였고, **5덱을 함께 고치는 수**(다른 덱이 안 쓰는 니케 교체·덱 간 맞교환)만 합을 올렸다.
   전원 보유·같은 육성이라는 랭커에 유리한 조건이다. → 결손 계정은 실험 5.
5. **로스터 결손** — 핵심 니케가 없거나 육성이 고르지 않은 계정에서 「랭커 구성 옮기기 + 대체」 대 탐색.
   **→ 완료** ([결과](experiments/05_roster_deficit/README.md), 시나리오 8개 · 탐색 각 800회 · 시뮬 6,232회):
   결손이 있으면 탐색이 기준선(랭커 300명을 옮겨 시뮬로 고른 최고)을 **+1~11%** 넘는다 — 무작위 3명 미보유 +4%,
   6명 +6~10%, 육성 불균형 +11%. 아무 랭커나 따라 한 경우 대비 +3~19%. 랭커가 이미 풀어 둔 결손(레드 후드 하나 없음)은 +0.8%.
   탐색은 빈자리를 메우는 대신 남은 핵심 니케를 **다른 덱으로 옮기고** 빈 덱을 랭커가 안 쓰는 니케로 새로 짰다.
   육성이 낮은 핵심 니케도 짝이 맞는 자리에선 쓴다(같은 6명이 없을 때보다 +5%). 300회면 800회 개선의 대부분(중앙 85%)이고,
   여러 랭커의 옮긴 덱을 다시 조립만 해도 시뮬 0회 추가로 +0.4~2.9%다.

## 범위

- **포함** — 계정별 유력 조합 군집, 여러 5덱 편성안, 배치·큐브·컨트롤 공동 탐색, 임의의 보스 패턴에 대한 적응,
  예산 관리, 랭커 데이터 활용, 필요시 대리 모델, 시뮬 검증과 실전 비교를 위한 근거 설명. 네 단계로 구현·검증한다.
- **제외** — 계산기 자체(외부 엔진을 연결만 한다), 육성 투자 판단, 계산 속도 최적화(당분간).

## 부산물 목표: 시뮬레이터 기반 티어

**우선순위는 본 목표(네 단계의 유력 편성 군집 탐색) 다음이다.** 본 목표를 해치지 않는 선에서, 설계할 때 이 용도를 막지 않도록
염두에 둔다(결과 캐시·추정 모델·가상 보스를 재사용할 수 있게).

- **왜** — 신캐는 랭커 기록이 없어 기존 방식(사용률)으로는 티어를 바로 정할 수 없다. 시뮬레이터만으로 정하고 싶다.
- **어떻게** — 니케 X의 가치 = X를 포함한 최적 5덱 점수 − X를 뺀 최적 5덱 점수 (대체 대비 기여, 야구 WAR와 같은 개념).
  실제 계산에서는 같은 조건·예산에서 찾은 최고값의 차이이며, 탐색 부족과 허용 운용 범위에 영향을 받는다.
  최적화기를 재사용하되 이 단일 점수로 본 목표의 후보군 다양성을 대신하지 않는다.
- **상황 의존도** — 여러 보스(가상 보스 포함)·조건에서 반복해 니케별 가치의 분포를 얻는다.
  평균 = 티어, 흩어진 정도 = 상황을 타는 정도(범용 vs 특정 상황 전용). 무엇을 타는지(속성인가, 특정 짝인가 —
  짝을 빼면 가치가 무너지는가)도 나눠 본다. 추정 모델의 짝 항이 이 정보다.
- **전제·걸림돌** — 평가기의 가상 보스 지원과 신캐 구현 속도·정확도. 기준 로스터 정의(전원 보유·동일 육성).
  니케마다 최적화를 다시 돌리는 연산량(캐시 재사용, 클라우드 사전 계산 규모면 감당 가능해 보임).

## 평가기(계산기)

평가기는 교체 가능하다. 최적화 쪽은 「스쿼드 + 배치 순서 + 육성 + 큐브 + 컨트롤 + 보스 조건·패턴 → 180초 딜」
인터페이스만 안다.

원본과 포크는 이미 데이터·로직이 갈라지고 있다(같은 스쿼드도 결과가 조금 다르다). 결과에는
어느 평가기·어느 버전으로 냈는지 함께 남긴다.

### 평가기 어댑터 — `nikke_opt/evaluator.py`

nikke-calc를 `python -m runner.sim --batch` 서브프로세스로만 부른다(계약: nikke-calc `docs/SIM-JSON.md`).
**요청 JSON v2**(`schema_version: 2`, nikke-calc `167698c`부터)를 보내고, 판이 다른 결과는 받지 않는다 — 평가기가 계약을 바꾸면 바로 끊긴다.

```bash
NIKKE_CALC_DIR=../nikke-calc python -m nikke_opt.eval "리틀 머메이드,크라운,라피 : 레드 후드,미하라,헬름" --boss "솔로 레이드 S40"
python -m unittest discover -s tests -t .      # 가짜 평가기로 돈다. NIKKE_CALC_DIR이 있으면 진짜로도 한 번
```

- **기대값 모드가 기본** — `sim.expected: true`, 1회로 결정론적이다. 평가는 언제나 180초(`sim.duration`은 거절).
- **요청 칸** — `EvalRequest(squad, boss, options)`의 `options`가 요청의 나머지 칸이다: `sim`(시드 등) · `enemy` · `operation`(카메라 · 택틱 · `auto`)
  · `profile`(육성, 아래) · `chars`(니케별 운용 — `control` dict · `cube` · `favorite_stage`). 2·3단계의 큐브·컨트롤을
  전달할 수 있는 기반이다. 입력 전달 지원과 해당 변수를 탐색·최적화하는 기능은 구분한다.
- **병렬** — `--batch` 프로세스 여러 개로 나눠 돈다. 프로세스 수만큼 거의 그대로 빨라진다.
- **캐시** — (평가기 커밋, 요청) → 결과. `.cache/evals.sqlite`(커밋 안 함). 평가기에 커밋 안 된 변경이 있으면 캐시하지 않는다.
  패턴 파일 등 외부 참조의 내용이 바뀌는 경우까지 식별하는지는 4단계에서 검증·보완해야 한다.
- **예산** — 실제로 돌린 시뮬 횟수만 센다(캐시 적중·같은 요청 중복은 안 셈). 넘칠 요청은 시작하지 않는다.
- **육성** — 요청에 인라인으로 싣는다. nikke-calc `profiles/`에 파일을 쓰지 않는다(그 폴더는 nikke-calc의 개인 데이터다).
  형식의 정본은 nikke-calc `docs/SIM-JSON.md` §육성(nikke-calc `a4174a5`부터).

  ```python
  EvalRequest(squad, boss=BOSS, options={"profile": {
      "base": "default",   # 적지 않은 니케 = 기본 스펙 (생략하면 미육성)
      "chars": {"크라운": {"skill_levels": "7/7/7", "overload": {"우월 코드 대미지": 2, "공격력": 1}}},
  }})
  ```

  요청 줄이 곧 육성이라 캐시 키가 내용을 따라간다. 프로필을 *이름*으로 주면(내 계정 `me` 등) 파일 내용 해시를 키에 넣는다.

조사 결과 (2026-10-07, nikke-calc `ba9f29c`):

| 항목 | 결과 |
|---|---|
| 호출 | CLI `--json` · `--batch`(JSON Lines). 결과에 평가기 커밋이 실린다 |
| 육성 | 기본 스펙(레벨 400·오버로드 등)이 전원에게 같다 + 니케별 운용 레이어(`char_defaults.json`, `auto`로 끔). 계정 육성은 `profile` — 처음엔 nikke-calc `profiles/<이름>.json` 파일로만 받았다(실험 5는 이름에 내용 해시를 넣어 우회). **2026-10-08 nikke-calc `a4174a5`부터 인라인 dict**(`base: "default"`면 적지 않은 니케 = 기본 스펙, 스킬·오버로드 줄 수 표기)를 받는다 — 위 「육성」. 빈 항목 = 기본 스펙과 딜 일치 |
| 보스 | 파라미터화 가능 — 가상 보스를 만들 수 있다 |
| 계약 v2 | **2026-10-08 nikke-calc `167698c`**: 입력이 요청 JSON 한 가지로 — `sim.*` · `enemy.*` · `operation.*` · `profile` · `chars.<니케>.control/cube`. 정본은 JSON Schema(`python -m runner.request`), 오류는 칸을 JSON Pointer `path`로 가리킨다. v1 배치 키(`expected` 등)는 거절. 실험 2·5 표본 12개가 `ba9f29c` 기록과 소수 8자리까지 같은 딜 |
| 운용 | 니케별 컨트롤은 dict, 큐브는 니케마다 따로(`chars.<니케>.cube`, 모르는·효과 모델 없는 큐브는 오류). 결과에 조작 요약 `control_detail` |
| 배치 순서 | **딜을 바꾼다.** 같은 5명 역순이 기본 적 −9%, S40 −24%. 순서도 탐색 대상이다 |
| 병렬 | 프로세스 병렬 안전, 결과 동일 |
| 1회 비용 | 4~5초. 4코어면 2천 회 약 40분 |
