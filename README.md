# nikke-opt

승리의 여신: 니케 **솔로 레이드 5덱(25인) 최적 편성 탐색기**.

> 내 육성 상태 · 이번 보스 · 허용된 평가 횟수가 주어지면, 그 예산 안에서 찾을 수 있는
> 가장 좋은 5덱(25명, 중복 없음)을 **180초 전체 시뮬레이션으로 검증해서** 내놓는다.

계산기는 만들지 않는다. 외부 계산기를 평가기로 붙여 쓰고, 이 레포는 **무엇을 돌려 볼지 고르고
어떻게 묶을지**만 맡는다.

---

## 배경

- 니케는 라이브 서비스 게임이다. 신규 니케가 계속 추가되고 시즌마다 보스가 바뀐다 → 매 시즌
  조합을 다시 고민해야 한다.
- 지난 시즌의 "정답"은 어느 정도 나와 있다. 많은 유저의 시행착오가 공유되며 덱이 수렴하고,
  특히 랭커 덱은 기록이 남는다(에닉 → [`nikke-analysis`](https://github.com/Jgaram/nikke-analysis)가
  시즌 1–41, 6개 서버, 서버별 상위 50명 × 5덱을 덱별 딜·전투력과 함께 수집).
- 하지만 **사람마다 육성이 다르고, 신캐가 나오면 조합이 바뀌고, 보스가 바뀌면 최적 덱이 바뀐다.**
  남의 덱을 그대로 따라가는 것만으로는 내 계정의 최적해가 되지 않는다.
- 단순 로직(탐욕적 선택 등)으로는 안 된다. 좋은 1·2덱은 누구나 비슷하게 짜지만, 승부는 대체
  자원(서브 딜러·버퍼)을 3~5덱에 어떻게 나눠 쓰느냐에서 갈린다.

## 문제 정의

| | |
|---|---|
| **입력** | 보유 니케와 육성 상태(레벨·오버로드·큐브·스킬 레벨·소장품 등) · 보스 조건(속성·방어력·패턴 스크립트) · 현재 니케 풀(신캐 포함) · **평가 예산 N** |
| **출력** | 서로 겹치지 않는 스쿼드 5개, 각 스쿼드의 배치(=버스트) 순서, 선택 근거 |
| **목표** | 5덱 **시뮬딜** 합 최대화. 실전딜과의 간극은 평가기(시뮬레이터) 쪽이 메울 일이고 이 레포의 관심사가 아니다 |
| **제약** | 한 니케는 25명 중 한 번만. 평가는 **항상 180초 전체 시뮬레이션** — 짧은 구간 측정으로 대신하지 않는다(초반 폭딜 덱을 과대평가한다) |
| **성질** | anytime — 언제 멈춰도 그때까지의 최선을 내놓고, 예산이 늘수록 결과가 좋아진다 |

### 예산은 평가 횟수로 센다

예산의 단위는 **벽시계 시간이 아니라 180초 시뮬레이션 횟수**다. 평가기 속도는 엔진 교체·병렬화·
포팅으로 얼마든지 바뀌지만(참고: 딜도로는 Rust 포팅으로 더 빠르다고 알려져 있다), "몇 번 돌려서
얼마나 좋은 답을 찾았나"는 엔진과 무관한 탐색 알고리즘의 성능이다. 시간 제한이 필요하면
`시간 ÷ 평가 1회 비용`으로 횟수로 바꿔 넘긴다. 계산 속도 최적화는 당분간 이 레포의 관심사가 아니다.

| 예산 N (감각) | 의미 |
|---|---|
| ~10회 | 5덱 한 벌 검증이 5회. 사실상 **사전 지식이 답을 내는** 구간 |
| ~수백 회 | 사전 지식 + 국소 개선 |
| ~수천 회 이상 | **탐색이 주도하는** 구간 |

### 풀 수 있는 문제인가

- **전역 최적의 증명은 불가능하다.** 평가기는 블랙박스이고, 보유 100명이면 5인 조합만 약 7,500만
  개에 배치 순서가 곱해진다.
- **"주어진 예산 안에서 최선"은 풀 수 있고, 얼마나 잘 풀었는지 잴 수 있다** — 이 레포의 목표는 이쪽이다.
  풀리는지 여부는 아래 [벤치마크](#성능-측정)의 예산-품질 곡선으로 실증한다.
- **게임 규칙을 하드코딩하지 않는다.** 버스트 순서·버충량·쿨감·시너지는 이미 평가기 안에 있다.
  이 레포가 푸는 것은 "비싼 블랙박스를 무엇으로 몇 번 돌려 볼까"(블랙박스 최적화)다. 구조 규칙은
  불가능한 조합을 걸러내는 데만 쓴다.
- **정답 데이터(라벨)는 매 시즌 시뮬레이터로 새로 만든다.** 랭커 데이터는 딜 수치로 쓸 수 없으므로
  (아래 「지식의 세 출처」) 라벨이 아니라 "무엇부터 돌려 볼지"의 사전 지식이다.

## 핵심 구조: 두 층으로 나눈다

덱끼리는 서로 영향을 주지 않는다(같은 보스를 각자 따로 친다). 따라서
**총점 = 스쿼드 점수의 합**이고, 문제가 둘로 갈린다.

1. **어떤 스쿼드가 좋은가 — 어려운 부분.** 평가가 비싸고 시너지가 합산되지 않는 블랙박스다.
   "다음에 무엇을 돌려 볼지"를 고르는 것이 이 레포의 본체이고, 데이터 분석·기계학습이 들어갈 자리다.
2. **겹치지 않게 5개 고르기 — 쉬운 부분.** 점수가 매겨진 후보 풀이 있으면 가중 집합 패킹이다.
   정수계획법으로 수만 개 후보에서도 정확한 최적해를 구한다.

## 지식의 세 출처

| 출처 | 강점 | 약점 |
|---|---|---|
| **랭커 덱** (에닉 → `nikke-analysis`) | 수많은 시행착오가 걸러진 결과. 사용률(티어)·자주 붙는 짝·버스트 구성 틀이 드러나 있고, 보스가 바뀌어도 대략적 추세는 비슷하다 | **딜 수치는 쓰지 않는다** — 랭커의 육성 정보가 없고, 과거 보스는 시뮬레이터에 없어 시뮬딜과 맞춰 볼 수 없다. 신캐·새 보스에는 기록이 없다 |
| **시뮬레이터** (외부 계산기) | 내 육성·이번 보스에 대한 실제 값 | 비싸다 |
| **구조 규칙** (버스트 단계 B1/B2/B3, 쿨감, 속성) | 불가능·무의미한 조합을 미리 제거 | 좋은 조합을 골라 주지는 못한다 |

## 접근 (초안)

```text
 후보 생성 ── 랭커 덱을 내 로스터로 옮기기(없는 니케는 대체) · 과거 데이터의 핵심 짝 · 구조 템플릿
     │
     ▼
 추정 점수 모델 ── 지금까지의 모든 180초 결과로 학습, 스쿼드 점수와 불확실성을 싸게 추정
     │
     ▼
 다음 평가 선택 ── 기대 점수 높음 / 불확실성 큼 (베이지안 최적화 · 능동 학습)
     │
     ▼
 180초 시뮬레이션 ── 결과는 전부 캐시하고 모델에 되먹임
     │
     ▼
 조립 ── 검증된 스쿼드로 정수계획법 → 최선 5덱 묶음
     │
     ▼
 국소 개선 ── 한두 명 교체 · 덱 간 맞교환 · 배치 순서 대안 (특히 3~5덱)
     │
     └──── 예산이 남았으면 위로 반복
```

- **기계학습의 역할은 추정 점수 모델(대리 모델)이다.** 처음엔 니케 단위 + 두 니케 짝 특징의 단순
  회귀로 시작하고 필요할 때 키운다. 강화학습처럼 끝에서 끝까지 배우는 방식은 필요 없다고 본다.
- **시즌 단위 사전 계산.** 보스가 공개되면 표준 육성으로 유력 스쿼드를 미리 돌려 캐시를 만들어 둔다.
  작은 예산의 실행도 따뜻한 상태에서 출발한다.
- **신캐 대응.** 랭커 데이터가 없으니 스킬 데이터에서 역할 태그를 뽑아 비슷한 기존 니케의 지식을
  빌리고, 부족한 만큼은 시뮬레이션으로 채운다.

## 성능 측정

이 시스템이 제대로 동작하는지는 다음으로 잰다. 모두 시뮬딜 기준이다.

- **랭커 구성 기준선** — 랭커 덱의 *구성*(5명 조합)을 **같은 육성·같은 보스로** 시뮬레이터에 돌린
  값보다 얼마나 나은가. (랭커 덱의 실전 딜과는 비교하지 않는다 — 육성도 보스도 다르다.)
- **기준 최적해** — 작은 로스터에서 막대한 예산으로 사실상 전수 탐색한 값과의 차이.
- **예산-품질 곡선** — N = 10 · 100 · 1,000 · 10,000에서 기준 최적해 대비 몇 %인가.

### 실험 기본 조건

- **육성**: 전원 동일한 가상 육성으로 시작한다(니케 차이가 육성 차이에 묻히지 않게).
- **보스**: 평가기가 지원하는 보스를 아직 확인하지 않았다. 단순한 가상 보스(고정 방어력·속성,
  패턴 최소)로 시작해도 된다.

### 사전 실험 (본격 구현 전에 "풀 만한가"를 확인)

1. **경향 안정성** — 랭커 데이터만으로, 시즌(보스)이 바뀔 때 사용률 순위·자주 붙는 짝이 얼마나
   유지되는지 잰다. 사전 지식을 얼마나 믿을지 정한다.
   **→ 완료** ([결과](experiments/01_trend_stability/README.md)): 니케 단위는 잘 맞고(과거 기반 상위 50명이
   이번 주력 25명의 90%, 나머지는 주로 신캐), 과거 스쿼드 ±1명이 덱의 76%를 덮는다. 짝은 보스마다 크게 바뀐다.
2. **점수 분포** — 한 보스·한 로스터에서 구조 규칙을 통과한 무작위 스쿼드 1~2천 개를 180초로 돌려
   딜 분포를 본다. 상위권이 얼마나 뾰족한지, 유효 후보가 얼마나 되는지.
3. **학습 가능성** — 2의 데이터로 "니케 단위 + 짝" 단순 모델이 처음 보는 조합의 순위를 맞히는지
   (순위 상관) 본다. 대리 모델이 필요한지, 가지치기 + 전수 탐색으로 충분한지 가른다.
4. **개선 여지** — 큰 예산으로 찾은 최선 5덱 vs 랭커 구성 기준선. 이 차이가 이 레포의 가치다.
   랭커 빈출 스쿼드가 이번 보스 시뮬에서도 상위권인지도 함께 보아 사전 지식의 쓸모를 잰다.

## 범위

- **포함** — 스쿼드 구성, 배치(버스트) 순서, 예산 관리, 랭커 데이터 활용, 추정 점수 모델, 근거 설명.
  **장기적으로** 큐브·컨트롤 같은 운용 변수도 탐색 대상에 넣는다.
- **제외** — 계산기 자체(외부 엔진을 연결만 한다), 육성 투자 판단, 계산 속도 최적화(당분간).

## 평가기(계산기)

평가기는 교체 가능하다. 최적화 쪽은 「스쿼드 + 배치 순서 + 육성 + 보스 조건 → 180초 딜」
인터페이스만 안다.

| 평가기 | 상태 | 메모 |
|---|---|---|
| [moris-kr/nikke-calc](https://github.com/moris-kr/nikke-calc) (TypeScript/Node) | **1차 대상** | 가장 활발히 유지보수. 2026-09-23 파이썬 엔진 제거, `site/src/engine/`이 정본. 기대값 모드 1회 약 0.9초 |
| [Jgaram/nikke-calc](https://github.com/Jgaram/nikke-calc) (Python) | 원본 | 유지보수 적음. 1회 약 6초 |
| 딜도로 | 비공개 | Rust 포팅, 더 빠른 것으로 알려짐 |

원본과 포크는 이미 데이터·로직이 갈라지고 있다(같은 스쿼드도 결과가 조금 다르다). 결과에는
어느 평가기·어느 버전으로 냈는지 함께 남긴다.

## 로드맵 (초안)

1. 교체 가능한 평가기 인터페이스 + 결과 캐시 (moris TS 엔진 연결)
2. 정수계획법 조립 + 랭커 덱 기반 후보 생성 → 첫 동작 버전
3. 벤치마크 (과거 시즌 재현 · 기준 최적해 · 예산-품질 곡선)
4. 추정 점수 모델 + 능동 탐색
5. 시즌 사전 계산 캐시 · 신캐 대응
6. 운용 변수(큐브·컨트롤) 탐색
